2026-08-19 | Orders + Dispatch + calc.js — closing out the #121 review | The last two review findings. (1) **Two per-tab Plant dropdowns survived the global selector.** #118/#119 gave Orders and Dispatch each their own Plant `filters` entry; #121 added the header control but left both in place, so the app shipped three plant filters. Orders' was worse than redundant — its options were a HARDCODED `[...PLANTS.map(p => p.name), UNATTRIBUTED_PLANT]`, so scoped to Hyderabad it still offered NPMD/Lepakshi/Tapi, every one of which could only ever return nothing. `CONTEXT.md` already listed "Plant filter (as a per-tab concept)" under _Avoid_ while two of them existed. (2) **The dispatch weight derivation existed twice**, in two files: `buildDispatchRecords` (App.jsx) and `filterDispatchesByPlant` (calc.js) each computed `Σ entry weight` and `vehicleWeight − that` with their own copy of the arithmetic. | Deleted both dropdowns — the Plant **column** stays on both tables, only the filter goes, and Orders keeps its other six chips (Type/Size/Status/Customer/Pending/Order month). That left `PLANTS` unused in App.jsx, so the import went too. Extracted `withDispatchEntries(record, entries)` into `calc.js` and pointed both call sites at it: it sets `bundleEntries`, `selectedBundles`, `theoreticalWeight` and `variance` together, naming the invariant that all three are **functions of the entries**. 3 new unit tests (344 total), including one asserting the filter path and a direct call produce identical weight and variance — the drift the duplication invited. Browser-verified: zero Plant chips on either tab, Plant column present on both, and one mixed 10 T invoice reading 7.0 + 3.0 stacked at All Plants and 7.0 scoped to Hyderabad. | **A global control is only global once the local ones it replaces are deleted.** Adding the header selector without removing the per-tab dropdowns produced the exact confusion the spec's "nobody has to reason about which views are scoped" was written to prevent, and a hardcoded options list made it visibly wrong (plants offered that cannot match a row). When a feature supersedes an older one, the older one is part of the diff. Second lesson, on the duplication: it was harmless the day it was written — both copies were correct — and that is precisely why it is worth extracting. The failure mode isn't today's wrong answer, it's next year's edit landing in one file and not the other, leaving one invoice weighing two different things depending on which code path last touched it. The helper's name states the invariant so the next person doesn't have to infer it.

2026-08-19 | Sales + Dispatch under the #121 plant filter | **Two-axis code review of the shipped #121 selector found a live data-loss path and a silently mixed-basis KPI — both from the same root cause: a filter was allowed to change what a WRITE and a RATIO mean, not just what is displayed.** (1) `Dispatch.softDelete` matches the RAW store by `id`, but the records it renders are plant-scoped shallow copies. Deleting while scoped to Hyderabad soft-deleted the **whole invoice**, including the NPMD lines the operator could not see and never intended to touch. (2) `SalesDashboard` received plant-scoped `orders`/`dispatches` but unfiltered `estimates` — a Best Estimate carries no plant, and `salesByDistributor` deliberately emits a row for every distributor holding one even with zero orders. So `beTotals.be` stayed company-wide while `kpis.mtdInvoice` went plant-scoped, and **% of BE / Gap to BE / the Plant BE achievement line quietly became one plant's actual over four plants' plan** — the exact four-against-one mismatch #117 exists to expose, reintroduced by the feature meant to reveal it. A third finding: `docs/DATA-MODEL.md` still claimed the 761.441/2615.441 MT split was "asserted against the real 18-Aug-2026 figures" after the LEARNINGS entry had already retracted that. | Neither is fixable by filtering harder — a per-plant Best Estimate is explicitly out of scope in #117, and `deleted` lives on the dispatch RECORD while plant lives on its entries, so there is no per-entry delete to fall back on. Both are therefore **withheld** under a filter and say why: `Dispatch` takes `plantScoped` and passes `onDelete={undefined}` (which drops DataTable's whole Actions column) beside an amber note; `SalesDashboard` takes `selectedPlant`, renders `—` with the reason in a `title` for % of BE and Gap to BE, and swaps the Plant BE achievement clause for "company-wide, not Hyderabad's". The **Best Estimate column itself stays and stays editable** — a company-wide plan is a correct company-wide number; only the comparison was ever wrong. The Sales CSV blanks the same two columns, because an exported mixed-basis figure outlives the screen that explained it. Docs corrected to say the tonnage split is unit-level only. Verified in Chromium against stubbed PostgREST reads (the #102 technique): All Plants reads "Plant BE 50.0 T · invoiced 20% of it" with Gap-to-BE total 40.0 and one Del button; Hyderabad reads the company-wide warning with Gap-to-BE "—" and zero Del buttons, while the Weight column correctly shows 7.0 T of the mixed 10 T invoice. 339 tests pass, `vite build` clean, no console errors. | **A filter is a way of LOOKING at data — the moment it changes what a write touches or what a ratio divides, it has stopped being a filter.** Both bugs passed the first review and the full unit suite because the filtering helpers themselves are correct in isolation; the defect only exists at the seam where scoped data meets an unscoped collaborator (`estimates`) or an unscoped write target (the raw store). Unit tests over pure helpers structurally cannot see that seam, which is the argument for the browser pass, not against the helpers. Durable rule for the next filter: enumerate every write and every DIVISION on the filtered screen, and for each ask "does this still mean the same thing?" — if not, disable it and say why, never let it silently return a different answer. Second lesson: retracting a claim in one file does not retract it everywhere. `add1ad8` corrected `LEARNINGS.md` and left the same claim standing in `DATA-MODEL.md`; grep the figure, not the file.

2026-08-17 | Sales tab — State → Region master (ticket #102) | Feature — show each distributor's **State** and **Region** on the Sales tab, region editable in place. Region is a business concept the ERP never exports; state now arrives with the data (#101). | Keyed the master by **state, not distributor**: new store `jsw:stateRegions` → `state_regions` (`unique(state)`, which is also the upsert arbiter — `CONFLICT_TARGET` in `db.js`), six seed rows in `src/data/stateRegions.js` with **fixed literal uuids**. `calc.js` gained `REGIONS`/`UNMAPPED_REGION`/`normStateName`/`stateRegionIndex`/`regionForState`/`distributorStateIndex`/`distributorRegionResolver`; `salesByDistributor` takes `opts.stateRegions` and returns `state`/`states`/`multiState`/`region` per row. `App.jsx` gained `RegionCell` (blue `<select>`, commits on change, `stopPropagation` so editing doesn't open the SKU drill-down) + State/Region columns + State/All States/Region in the Sales CSV. 15 new unit tests (247 total), `vite build` clean, and a throwaway Playwright smoke test (stubbed PostgREST reads) confirmed the render, the `+1` multi-state marker, the totals row, and that the write lands as `POST state_regions?on_conflict=state`. | **The store's "table if non-empty, else fallback" pattern is not enough for a seeded master that is edited one row at a time.** Editing one state writes ONE row, so on the next load the table is non-empty and the fallback never fires — the other five seeded states would silently read `Unmapped`. Fix: `stateRegionIndex` **layers the seed under the stored rows** rather than choosing between them, which also makes "an edited region overrides the seed" fall out for free. Corollary: clearing a region must store `region: ''` (an explicit un-mapping) instead of soft-deleting the row, or the seed would spring back. Second lesson: a missing mapping is a **labelling** gap — `Unmapped` is not a fifth region and its tonnage stays in every total, which is asserted by summing the rows grouped by region back to `salesKpis`. Also found: the two existing e2e specs have been failing on `main` since the July 2026 login gate landed — they `goto('/')` and never seed `jsw:auth`, so they hit `LoginGate` and no tab buttons exist (verified in a clean `main` worktree; not fixed here, out of scope).

2026-07-01 | Stage 4 (Dispatch) | **~50 SKUs showed negative stock — the ERP invoice file had been imported twice, so dispatched tonnage was stored at exactly 2.00× reality.** Reconciled the SKU report against the invoice file: `Inventory = Production − Dispatched`, and dispatched was double, so ~1,257 T of phantom negative stock across 50 SKUs; the ratio `(Production − Inventory)/fileInvoiced` was a clean **2.00** for all 42 file-present SKUs. Root cause in `onUpload` (`src/App.jsx`): dedup was **per-invoice** via `existingInvoices = Set(dispatches.map(d=>d.invoiceNo))` and skipped a row only when `r.invoiceNo && has(...)` — so a **blank invoice number bypassed it entirely**, it never caught **duplicate lines within one file**, and the blank-invoice grouping key used the **row index** `i` (a re-upload minted fresh records). Separately the operator switched to a cleaner **"One Helix"** invoice export (Zoho) that carries the same 1,931.4 MT / 81 invoices but has **no MM ID, no Sku ID, no pieces** — only Item Name (== SKU description, resolves 100% by description), Quantity (MT), Invoice Number, Customer Name, PurchaseOrder (== the old Child Order ID). | Rewrote the importer for **One Helix only** + made it **idempotent per line** + a **Replace mode** for the one-time rebuild. New pure helpers in `calc.js`: `dispatchLineKey(line)` = normalised composite `invoiceNo | skuCode | weight(3dp)` (format-independent, so it dedups across the old ERP shape too — unlike a per-line Sku ID only the ERP file has), and `dedupeDispatchLines(existing, parsed)` → `{toImport, skippedDuplicateLines, skippedInvoices}` (scoped to **non-deleted** so soft-delete-then-reupload corrections still work; a `seenThisBatch` set kills within-file dupes). `mapDispatchRow` now maps One Helix headers (`itemname`→desc, unit-aware `quantity`→weight, `purchaseorder`→childOrderId); `onUpload` resolves SKU by description→canonical, dedups on the resolved lines, drops the row-index grouping fallback, and the summary reads `0 new lines — N duplicate line(s) skipped` on a clean re-upload. **Replace mode** soft-deletes current records then imports fresh (guarded confirm; reversible). Verified E2E against the real file: 288 lines / 1,931.4 MT import once, a second upload imports **0** (288 skipped). 114 unit tests pass (8 new), `vite build` clean. | **Dedup at the granularity of the thing that double-counts — the LINE, not the invoice — and never let a fallback key depend on row index.** Deliberately did **not** add a DB unique constraint: dispatch lines live nested in a `bundle_entries` JSONB array (no per-line column to constrain), and an invoice-level index would fight the optimistic upsert-on-`id` sync + the soft-delete rebuild. **Impact check (the ask):** the negative-stock report, Coil Tracker, Dashboard KPIs, Invoice Reconciliation + CSV, and cost reconciliation are **unaffected** (they read skuCode/weight/date/coilAllocations, all present or derived). Only the **Sales Dashboard / Order Backlog** degrade slightly — the One Helix file lacks the per-order-**line** `Sku ID`, so `shippedByOrderLine` (which has an `if(lid)` guard, calc.js:322 — lines are skipped, NOT mis-bucketed) loses per-line netting; but `orderLineInvoiced` falls back to the order sheet's own `invoicedQty` and distributor grouping is preserved via `childOrderId` (from PurchaseOrder → `resolveDistributorIdentity` byChild), so customer- and per-order totals stay right — only the split within a multi-line order loses precision. Applied the gstack office-hours (narrowest wedge: switch to the clean source) + plan-eng-review (blast-radius impact map, reversible replace, failure modes) lenses while planning.

2026-06-26 | Sales dashboard | Bug — one distributor (**V V N STEELS P LTD**) showed as **two rows** | `distributorSalesRows` grouped distributors by the **free-text name** keyed with only `.trim()` (no whitespace/case normalisation), so the same party spelled differently between the Orders sheet and the (older, stored) Invoice records formed two groups; the 2-word display code ("V V") made them look like a duplicate.
