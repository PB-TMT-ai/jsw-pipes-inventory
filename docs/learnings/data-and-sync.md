2026-08-20 | `replaceAllRows` in src/lib/db.js — the delete-before-insert that turned a rejected write into an empty order book | Follow-up to the entry below, which fixed the missing column and left the mechanism that made it catastrophic. `replaceAllRows` superseded FIRST and inserted SECOND, in two separate HTTP round-trips with no transaction spanning them. So the class of failure was never "the plant column is missing" — it was **any** rejected insert (a new column, one bad row, a dropped connection, a expired token mid-upload) wiping the table it was rebuilding. `orders` is hard-superseded and lost the rows outright; `dispatches` is soft-superseded and would have hidden them. The tempting fix — one Postgres function doing both inside a transaction — is the wrong one HERE, and for a pointed reason: it is DDL, and un-run DDL is precisely what emptied the book. A fix that only works once somebody remembers to run SQL does not fix this bug. | Inverted the order: (1) read the live ids server-side, (2) insert the rebuilt set, rolling the inserted chunks back if any chunk is rejected, (3) only then supersede exactly the ids from step 1. Pure app-side, no schema change. Step 3 can no longer use a predicate (`neq('id', <impossible>)` / `eq('deleted', false)` would both match the rows just inserted), so it is scoped to the id list — chunked at a new `ID_FILTER_CHUNK` of **100**, not the body's 200, because `.in('id', […])` rides in the query string where 200 UUIDs is ~7.8 KB against a ~8 KB request-line limit. A supersede failure deliberately does NOT roll the new rows back. `emitSyncError` gained a `recovery` sentence and `SyncErrorBanner` shows it instead of its generic "changes will NOT persist" tail. Nine tests, each watched failing against a deliberately reintroduced defect: swapping steps 2 and 3 reds three of them, deleting the rollback reds one, setting `ID_FILTER_CHUNK` back to 200 reds one. Docs in `docs/DATA-MODEL.md`. NOT done: the two steps are still not atomic, and the unchunked `.delete().in('id', legacyDeleted)` in `pull()` (coils/baby_coils legacy purge) has the same URL-length exposure and was left alone as out of scope. | Two. (1) **Pick the invariant, then let it decide every failure path.** The invariant here is *a failed upload never leaves fewer rows than it started with — worst case duplicates, and a re-upload heals them*. Stated, it settles arguments that otherwise go in circles: should a failed supersede roll the new rows back? No — that trades the healable failure for the unhealable one. Should a failed rollback throw? No — it would bury the error that says why. Both answers fall out of the invariant rather than out of taste, and "duplicates are recoverable, loss is not" is the asymmetry doing the work. (2) **The July fix and the August fix look like opposites and are not.** July said "never supersede from a list of ids"; August needs a list of ids. The reconciliation is that July's real defect was the list coming from a **page-load snapshot**, not that it was a list — a server-side read issued inside the write has none of that staleness. A rule written down as its remedy ("use a predicate") rather than its cause ("don't trust stale local state") is a rule that will eventually block its own successor, and this one nearly did.

(1) **DDL in a file that nobody dares run is not a migration.** `supabase-setup.sql` is a *bootstrap* file; the moment it also carries `delete from …` it stops being safe to re-run, and every `add column if not exists` inside it becomes a statement that will never reach a live database. Ticket #118 passed its tests, passed review and shipped — because every test runs against a schema built from that file, so the tests and the repo agreed with each other and neither had ever met production. **A schema change needs its own extracted, guarded, re-runnable file, or it has not shipped.** Two tickets have now landed this way (#125/#126 locked users out; #118 emptied the order book); that is a pattern, not an accident. The safe shape is stage-then-swap, or one RPC that does both inside a transaction. (3) **"The schema cache" in a PostgREST error is a real component, not a figure of speech** — it is worth reloading explicitly so nobody concludes the SQL failed when it was only unread.
